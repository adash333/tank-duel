# /save-prompt

## 目的と自動実行

このリポジトリで受けたユーザーの依頼と結果を保存する。ユーザーが `/save-prompt` を指定したとき、および通常の依頼への対応が終わったときに実行する。質問への回答や作業途中に追加された指示も記録対象にする。

ユーザーは、記録の保存、すべての変更のステージング、通常のコミットとmainへのpushを継続的に許可している。毎回確認を取り直さず実行する。ユーザーが今回の保存やpushを不要と指定した場合は、その指示を優先する。

## 保存内容

1. 会話から、まだ記録していないユーザーのメッセージ本文を取り出す。
2. **「プロンプト本文」には原文をそのまま保存する。** 全角・半角の空白、改行、句読点、表記を変更せず、言い換え、整形、省略、誤字修正をしない。ツール呼び出しや環境情報のラッパーを本文に混ぜない。
3. 原文はコードフェンスで囲む。本文がフェンスを含む場合は、それより長いフェンスを使い、原文を変えずに保存する。
4. **「結果」には、実際に行った変更、作成・変更したファイル、検証結果、必要なURL、未完了事項を要約する。** 未検証・未公開のものを完了と記載しない。
5. 一つの依頼に複数の指示・補足・質問が続いた場合、それぞれの原文と結果を区別して記載する。すでに記録した原文を重複追加しない。

## 保存先とファイル名

- 保存先はリポジトリルートの `docs/prompt/`。
- 日付は実行日のユーザーのタイムゾーンで `YYMMDD` とする。タイムゾーンが不明なら実行環境の日付を使う。
- 同日に一つの流れだけなら `YYMMDD-題名.md` とする。例：`261012-戦車ゲーム.md`。
- 同日の既存記録を先に読み、同じ依頼・機能・一連の作業に属するものは既存の一つのMarkdownファイルへ追記する。依頼ごとに別ファイルを作らない。
- 同日に独立した別の流れが増える場合は `YYMMDD-01-題名.md`、`YYMMDD-02-題名.md` のように2桁の連番を使う。必要なら、その日の最初の無番号ファイルを `01` 付きに改名し、リポジトリ内の参照も更新する。
- 既存の番号は再利用せず、最大番号の次を採用する。別の日の記録とは結合せず、必要な場合は前日のファイルを参照する。
- 題名は内容がわかる短い表現にし、パス区切り文字を含めない。

## Gitへの反映

1. リポジトリルートで現在のブランチ、`git status`、リモートmainを確認する。既存のユーザー変更を保持する。
2. mainの最新履歴に基づいて記録を保存する。他のブランチで作業している場合は、その変更を保持したままmainへ通常の方法で反映する。履歴を失う強制切替・reset・force pushは使わない。
3. 記録を含め、**それまでのすべての変更**を以下でステージングする。追加・変更・削除を対象にし、既存の `.gitignore` は尊重する。

   ```sh
   git add -A
   ```

4. ステージングされた差分を確認し、変更があれば内容を説明するコミットをmainに作る。空コミットは作らない。実際の変更に応じた必要なチェックを済ませ、同じ入力で成功済みのチェックは理由なく繰り返さない。
5. 以下を実行し、mainへpushする。

   ```sh
   git push origin main
   ```

6. リモートの更新を確認する。競合・権限不足・接続失敗を成功扱いせず、できる範囲の修復を行う。CLIによる通信が使えずGitHub接続が使える場合は、同じステージング済みの変更をGitHubのtree/commit/ref操作でmainへ反映してよい。現在のmainを親にし、既存の変更を保持し、期待する先頭SHAを確認して更新する。
7. 完了時に保存先、コミット、mainへの反映結果を簡潔に伝える。現在作成するコミット自身のSHAを書き込むためだけに記録を編集・再コミットする循環を作らない。コミット前の記録では、まだ完了していないpushを完了と断定しない。

## 記録の基本形

```markdown
# 題名

日付：YYYY-MM-DD

## 依頼1

### プロンプト本文

（ここにコードフェンスで囲んだ原文をそのまま保存）

### 結果

実施した変更・検証・未完了事項の要約。

## 依頼2

同じ流れの追加の原文と結果。
```

このスキルはリポジトリ内の作業に適用する。別のリポジトリやアカウント全体の実行設定を変更したとは扱わない。
